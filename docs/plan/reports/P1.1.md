# P1.1 — STAC search + same-track pair selection

## What was built
- `src/cutoff/data/cdse.py`: `Scene` (frozen dataclass with the plan's fields, plus `product_uuid` for the OData
  download in P1.7), `search_s1(bbox, start, end, stac_url)`, `scenes_from_items(items, aoi)`, `aoi_coverage`
  (AOI fraction covered by the item footprint, both projected to the AOI's UTM zone after densifying the edges).
  - `start`/`end` come from `start_datetime`/`end_datetime`, else from the `_YYYYMMDDTHHMMSS_YYYYMMDDTHHMMSS_` part
    of the item id.
  - Items with the same product stem (name without the 4-char unique id and `_COG`) are deduped; the newest
    `processing:datetime` wins.
  - Non-IW items are skipped, because every backend requests `acquisitionMode: IW`.
- `src/cutoff/data/s1_pairs.py`: `NoValidPair`, `select_pairs(...)` with the plan's signature and defaults, and
  `pair_to_json`.
  - Post strictly after the event. Pre strictly before it, on the same `(rel_orbit, direction)`, newest first.
  - Scenes without VV+VH, or with coverage < `min_coverage`, are rejected.
  - Ranking: earliest post, then coverage, then number of pre scenes.
  - The `NoValidPair` message lists every track seen, its last pass, and the next expected pass (last + 12 d).
  - `allow_cross_track=True` (E5 only) returns pairs whose pre scenes come from one other track (newest pre first),
    flagged `"cross_track": True`.

The plan's cases are all covered:
- event `2026-08-26T02:52Z` → 85 ascending, post `2026-08-28T12:21:41.76Z`, pre [08-16, 08-04, 07-23],
  `post_lag_hours` = 57.49;
- event `2026-08-28T13:00Z` → post 2026-08-31 (121 descending), never 08-28;
- only cross-track candidates → `NoValidPair` listing the tracks and the next passes (09-09 for 85A, 09-05 for 19D);
- no VH → rejected; coverage < 0.8 → rejected;
- `allow_cross_track=True` → `"cross_track": True`, post 85A 08-28, pre 19D starting with 08-24.

## Finding: track 121D covers only part of Trishuli (affects D3 alternates and E5)
The 121D footprint's west edge runs diagonally from (85.23E, 27.48N) to (85.47E, 29.00N). Measured coverage in UTM:

| AOI | 85A | 19D | 121D |
|---|---|---|---|
| fixture bbox 85.2–85.5 / 28.0–28.3 | 1.00 | 1.00 | 0.55 |
| trishuli_north 85.28,28.10,85.42,28.29 | 1.00 | 1.00 | **0.555** |
| trishuli_south 85.10,27.88,85.30,28.10 | 1.00 | 1.00 | **0.004** |

So under the plan's `min_coverage = 0.8`, 121D is never selected on the Trishuli run AOIs. For event `08-28T13:00Z`
on trishuli_north, the selector picks **19D, post 2026-09-05**. The rule was not changed.
- The 121D expectation (`test_post_must_be_strictly_after_event`) is tested on an AOI inside the fixture bbox that
  all three tracks cover fully (85.40, 28.05, 85.50, 28.25).
- `test_coverage_rejects_121d_on_trishuli_north` pins the real trishuli_north behaviour.
- The D3 alternate "121D (post 08-31)" is therefore not usable at 80 % coverage on trishuli_north; 19D is.
  This does not affect E5, which uses 19D pre + 85A post.

## Deviations
None in the rules. Two additions: `Scene.product_uuid` (an optional field at the end) and `pair_to_json`.
